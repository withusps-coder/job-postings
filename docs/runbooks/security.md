# Security runbook: retiring the legacy browser admin credentials

## Purpose and current containment state

The legacy static site contains a client-side numeric PIN gate and accepted a GitHub personal access token (PAT) in the browser for direct GitHub API writes. This was not an authorization boundary: anyone able to read the public page could inspect the gate logic, and a browser-stored token could be exfiltrated by browser compromise or script injection.

Treat the legacy PIN and every PAT ever entered through that page as compromised. The legacy PIN must not be reused for Cloudflare Access, GitHub, email, device, or any other account. The existing public page must not receive a replacement PAT, and no browser or Git publication path may be restored.

Local containment completed for this migration phase:

- The hazardous flow was inventoried without recording its PIN or token value.
- No credential was copied into source, evidence, shell history, or this runbook.
- After cutover, protected Functions use Cloudflare Access, D1, and private R2. The repository's JSON, generated HTML, Git history, and the legacy site are never public-content authority or a runtime fallback.

External containment remains mandatory: revoke the previously entered PAT in GitHub settings. If its identity cannot be established without exposing it, revoke every token that may have been entered into the page. Do not create a replacement PAT. The redacted blocker/evidence record is in `.omo/evidence/task-1-personal-recruiter-site/credential-revocation-status.md`.

## Replacement trust boundaries

The replacement uses the following boundaries. Host admission occurs before any D1 or R2 read.

| ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Canonical host admission                                                                                                                    | Admin Functions accept only the configured exact HTTPS canonical host and origin for their environment. They require the request URL host, `Host`, forwarded host, and `Forwarded` host to agree. Production public reads on the configured default Pages host redirect to the configured canonical public origin; preview aliases, alternate/legacy hosts, and unconfigured hosts are denied. An explicitly configured loopback host/origin is permitted only for local tests. | Wildcards, Pages preview aliases, alternate domains, legacy hosts, or redirecting admin requests.                                                                                                                               |
| Administrator identity                                                                                                                      | Before an admin route reads D1 or R2, validate the `cf-access-jwt-assertion` as RS256 against the configured Access JWKS; require the exact issuer, audience, expiry, subject, and approved administrator email.                                                                                                                                                                                                                                                                | Shared PINs, broad email policies, bespoke browser sessions, or trusting an unverified assertion.                                                                                                                               |
| Mutation integrity                                                                                                                          | Require the exact configured `Origin`, `Sec-Fetch-Site: same-origin`, and a fresh subject-bound CSRF token signed by the environment-specific `CSRF_SIGNING_SECRET`. Mutation responses have no CORS grant and use `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`.                                                                                                                                                                                             | Cross-origin mutation, a stale or unbound CSRF token, or a browser-held signing secret.                                                                                                                                         |

Public listing, detail, sitemap, and media routes render only the active immutable D1 revision and its immutable asset bindings. Use separate production and staging values and bindings. Never put secrets, administrator identities, tokens, cookies, assertion headers, request bodies, or personal data in committed `.env`/`.dev.vars` files, build logs, screenshots, terminal captures, analytics, or error responses.

## Rotation procedure

Rotate or restrict the affected provider boundary immediately after suspected exposure, administrator departure, policy scope expansion, or credential expiry. Rotate one boundary at a time so retained D1/R2 state remains recoverable.

1. Record the incident time, affected boundary, and provider-side identifier only in the approved private incident system. Do not put a secret value in Git, issue trackers, chat, or evidence.
2. Revoke or restrict the affected Access policy, provider credential, or binding in the provider control plane. For the legacy browser flow, revoke all candidate old PATs if attribution is uncertain.
3. Use the provider-approved rotation or configuration procedure with the least privilege required by that boundary. Do not add a repository publishing credential or substitute a browser-held secret.
4. Set an existing runtime secret only through the provider's encrypted non-echoing secret flow. Never place a secret in source, a shell command, shell history, process arguments, or evidence.
5. Exercise a harmless protected read or operation-specific same-key terminal replay on the exact canonical host. Capture only status code, timestamp, safe route, and provider request/correlation ID after redaction.
6. Verify the old credential or policy is no longer usable, invalidate related sessions where applicable, and inspect Access, Pages, D1, and R2 audit logs for unexpected use. Do not test an old secret from a terminal, browser console, or evidence capture.
7. Update the private credential inventory with scope, resource, owner, creation date, expiry date, and rotation date. Record only a provider-side identifier or fingerprint, never the credential value.

## Incident response

1. **Contain:** stop legacy admin use; revoke the suspected credential; remove or restrict the affected Access policy or deployment binding if needed.
2. **Assess:** review Access, Pages, D1, and R2 audit/activity logs for authentication failures, deployment changes, binding changes, operation failures, and unexpected reads from the suspected exposure window.
3. **Eradicate:** remove browser token storage and client-side write code; correct only the affected provider boundary; do not create a replacement PAT or a static/Git publishing path.
4. **Recover:** validate that public routes use the exact canonical host and active immutable D1 revision, admin routes require the exact Access identity and CSRF checks, and private drafts and R2 objects remain retained. Use the normal protected close or rollback operation rather than raw D1/R2 mutation.
5. **Learn:** record a redacted timeline, scope correction, and follow-up owner. If a secret was committed, coordinate the approved repository and provider security response; do not rewrite history as improvised containment.

## Evidence and redaction rules

Evidence may include timestamps, file paths, line ranges, HTTP status codes, safe response headers, SHA-256 hashes, immutable R2 key references, D1 revision identifiers, and redacted screenshots. It must never include tokens, PINs, OTPs, cookies, Authorization headers, Access assertions, administrator email addresses, user identifiers, raw browser storage, full request bodies, or personal data.

Before publishing or sharing evidence, run the repository-approved secret-pattern scan against the evidence directory. Reject current and legacy token patterns and standalone six-digit numeric values, then review all redaction failures manually. A passing automated scan is not proof that a capture is safe.

## Rollback and operational constraints

Do not restore the client-side PIN/PAT flow, a browser/Git publication path, or any legacy/static public-data fallback. Use the protected `/admin/` workspace on the exact canonical host to perform close or rollback. Rollback creates a new immutable D1 revision from a retained source revision and atomically advances the active pointer; it does not mutate the retained source. Retain D1 revisions, asset rows, and private R2 objects indefinitely: detach, close, and rollback are state transitions and never authorize physical deletion.
